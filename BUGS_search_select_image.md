# Bug Handoff: Search, Selection & Image (scent-cast)

The "add to vault" search lives in `artifacts/scent-cast/src/components/FragranceCapture.tsx` (search input + results list + select + confirm), wired to `App.tsx:501` via `onAdd={handleAddItem}` (the actual vault POST is in `context/WardrobeContext.tsx:755`). Search/detail HTTP goes through `src/lib/fragranceApi.ts`. The vault image editor ("choose what looks wrong" / "reimagine") lives in `components/Wardrobe.tsx`. Two facts shape these bugs: (1) live search **candidates come from Google `site:fragrantica.com`** in the external Python engine, so short/acronym queries return nothing useful and there is **no acronym/brand-alias normalization anywhere** before the query is sent; (2) image resolution on save is **deferred by design** (returns no image immediately, backfills the shared catalog in the background, and the tile self-heals on the next ~60s wardrobe poll via `batchHydrateImageUrls`). **Serper key note:** keys load as a *pool* (`SERPER_API_KEYS` plural + legacy singular `SERPER_API_KEY`, `serperService.ts:45`); a 402 retires only that one key. The production pool key ("deeper key") is healthy — only the singular `SERPER_API_KEY` in `ScentCast.env` is stale (local-dev only). So Serper exhaustion is **not** the production root cause of any bug here.

## BUG 1 — Acronym search returns nothing
**Symptom:** "MFK" (Maison Francis Kurkdjian) returns 0 results.
**Root cause:** No acronym/brand-alias expansion exists. `FragranceCapture.tsx:382` sends the raw query to `searchFragrances`, which forwards it raw to the engine (`fragranceApi.ts:1228`, `encodeURIComponent(query)`). The external engine resolves candidates via Google `site:fragrantica.com mfk`, which returns nothing relevant, so the engine returns no usable rows. The SPA's own filter would actually *accept* an MFK row if one existed — `searchResultMatchesQueryIntent` (`fragranceApi.ts:1089-1108`) builds `normalizedInitials(house)` ("mfk") into its match string — so the failure is upstream (query never expanded to the brand name), not the client filter.
**Key files:** `FragranceCapture.tsx:355-444` (handleSearch, no normalization) · `fragranceApi.ts:1218-1290` (searchFragrances, raw passthrough) · `fragranceApi.ts:1076-1118` (initials-aware result filter — already MFK-friendly).
**Fix direction:** Add a brand-acronym/alias map on the SPA before sending (expand "mfk" → "Maison Francis Kurkdjian"), or query both raw + expanded and merge. Confirm engine-side `site:` query shape if expansion alone is insufficient. No min-length gate is involved (form-submit only; no debounce).
**Confidence:** High (mechanism), Med (that engine returns nothing for "mfk" specifically — not directly observable here; consistent with known fact #1).

## BUG 2 — Brand-dump + slow
**Symptom:** "Tom Ford Lost Cherry" → ~4s, returns all Tom Ford fragrances, "Lost Cherry" not ranked first.
**Root cause (ranking):** The SPA does **zero client-side relevance ranking**. Results are rendered in engine order (`FragranceCapture.tsx:384-399` maps and `setMatches(nextMatches)` with no sort; `setSelectedIdx(0)` just picks index 0). The engine returns the whole brand (known fact #3) and the SPA preserves that order, so the specific scent is buried. `searchResultMatchesQueryIntent` only *filters* (≥50% token overlap), it does not *rank*.
**Root cause (latency):** Sequential awaits in `searchFragrances`: primary engine call, then `shouldSupplementWithAppSearch` (`fragranceApi.ts:1152-1162`) fires a **second** awaited request to the Express app-search and `mergeSearchResults` when the engine returns < 8 results or a brand-only set. The brand dump itself is the slow Google-backed engine call; the supplemental round-trip adds more.
**Key files:** `FragranceCapture.tsx:384-431` (no sort) · `fragranceApi.ts:1273-1289` (sequential supplemental search) · `fragranceApi.ts:1089-1108` (filter, not ranker).
**Fix direction:** Add a client relevance sort keyed on the query (exact name match > name token coverage > brand-only), applied before `setMatches`; default `selectedIdx` to the top-ranked match. For latency: skip/parallelize the supplemental app-search when the primary already has a confident name hit.
**Confidence:** High.

## BUG 3 — No selected-state feedback
**Symptom:** Tapping a result shows no clear "this one is selected" signal.
**Root cause:** Selection state exists but is visually indistinguishable. `index.css:438-441` styles `.scent-vault-result-card:hover` and `.scent-vault-result-card.is-selected` with the **same** `border-color`/`box-shadow`, so a selected card looks identical to a hovered one (and touch devices have no hover baseline to contrast against). Compounding it, `handleSearch` auto-selects index 0 (`FragranceCapture.tsx:431`), so "selected" is the default state, not a felt response to the tap. There IS a tap handler + `aria-pressed` + a "Selected — ready to add" line (`FragranceCapture.tsx:880-918`), but the visual weight is too low.
**Key files:** `FragranceCapture.tsx:876-902` (item button, `is-selected` toggle) · `index.css:411-441` (selected==hover styling) · `FragranceCapture.tsx:431` (auto-select index 0).
**Fix direction:** Give `.is-selected` a distinct treatment (checkmark, accent fill/ring, brighter border than hover); consider not auto-selecting so the first tap produces a visible change. This is the only search-results list in the app — no separate dropdown component exists.
**Confidence:** High.

## BUG 4 — Confusing select→add-to-vault flow
**Symptom:** After tapping a result users don't know how to actually add it.
**Root cause:** A tap only **selects** (`onClick={() => setSelectedIdx(i)}`, `FragranceCapture.tsx:880`) — it does not open a detail modal or add. The actual add is a **separate second action**: the "Add to Vault" button (`FragranceCapture.tsx:919-928`) → `handleConfirm` (`:446`) → `onAdd` (`:457`/`:628`) → `WardrobeContext.handleAddItem` (`:755`) → `POST /api/wardrobe`. The two-step (tap-to-select, then find/press a separate button) combined with the weak selected-state of Bug 3 leaves users unsure a tap did anything. The button label does switch "Select a Result" → "Add to Vault" (`:926`) but only after selection, and it sits below a scrollable results panel so it can be off-screen.
**Key files:** `FragranceCapture.tsx:880` (tap=select only) · `:919-928` (separate Add button) · `:446-690` (handleConfirm: detail fetch → `/api/scent-profile` → `onAdd`) · `WardrobeContext.tsx:755-831` (POST). Note: add is a **direct fetch**, not an api-client-react hook.
**Fix direction:** Tighten the loop — e.g. make tap immediately stage + reveal a prominent sticky "Add to Vault" CTA, or collapse to single-tap-add for single results; ensure the CTA is always visible (sticky footer) and the selected card visibly bound to it. Strongly coupled to Bug 3 (fix together).
**Confidence:** High.

## BUG 5 — Saved fragrance has "No image"
**Symptom:** Fragrance saved but showed "No image"; user fixed it manually via the editor (choose "Multiple bottles / lineup" → reimagine).
**Root cause (a — deferred resolution returns nothing on save, by design):** Save resolves the image through `POST /api/scent-profile` (`FragranceCapture.tsx:576`) → `buildProfile` with `imageResolution: "deferred"` (`scent.ts:164`). Deferred returns **only** an already-cached catalog image (`scentEngineCore.ts:266-272`); a never-seen fragrance has no cache hit → `cleanImageUrl = null` → profile `imageUrl: undefined`. Client receives `pipelineImageUrl = ""` (`FragranceCapture.tsx:614`) and saves the vault row with `imageUrl: ""` (`:645`). So **every brand-new fragrance saves imageless and shows "No image" immediately** — independent of any key.
**Root cause (b — backfill targets the catalog, tile relies on poll to self-heal):** After the empty save, `scentEngineCore.ts:364` fires a background `resolveImageNow()` that, on success, writes the image **only to the global catalog** (`saveCatalogEntry`, `:368`) — NOT the user's `user_fragrances` row. The tile recovers only because `GET /api/wardrobe` re-hydrates every row from the shared catalog via `batchHydrateImageUrls` (`wardrobe.ts:116`) on load and on the 60s background poll (`WardrobeContext.tsx:735`). So on the happy path the image appears after a delay (up to ~60s), not on save. If the background backfill produces no image (genuinely no candidate for an obscure fragrance — or, in **local dev only**, the stale `ScentCast.env` Serper key), the catalog stays empty and the tile stays "No image" with no user-facing recovery prompt.
**Root cause (c — placeholder):** `BottleImage.tsx:157,167` renders "No image" whenever `!url`.
**Root cause (d — why manual worked):** The editor in `Wardrobe.tsx` has two paths. The "choose what looks wrong" dropdown (`Wardrobe.tsx:1984`, options from `imageRefreshSolvers.ts`) drives `handleRefreshImage` (`:1155`, `POST /api/refresh-bottle-image`, Serper-backed). The "Reimagine" button drives `handleReimagine` (`:1213`, `POST /api/reimagine-bottle-image`) → `reimagineService.ts`, which uses **OpenAI `gpt-image-2` image-edits, not Serper**. Caveat: reimagine **requires an existing source image** (`Wardrobe.tsx:1217` "No image to reimagine — find one first"), so a truly image-less tile must get a raw image (refresh, which on a healthy pool key succeeds) before reimagine can run; verify the user's exact sequence.
**Key files:** `scent.ts:151-167` (deferred) · `scentEngineCore.ts:266-383` (deferred return + background catalog-only backfill) · `wardrobe.ts:103-119` (GET hydrates from catalog) · `WardrobeContext.tsx:732-753` (60s poll) · `imagePipeline.ts:489-500` (null on no candidates) · `BottleImage.tsx:157-169` (placeholder) · `Wardrobe.tsx:1155-1308` (refresh=Serper, reimagine=OpenAI) · `reimagineService.ts:291-439`.
**Fix direction:** This is mostly a UX/timing gap, not infra. (1) On the new tile show a "fetching image…" loading state instead of bare "No image" while the deferred backfill + poll completes; consider triggering an immediate one-shot re-hydrate (or a short-interval poll) right after save instead of waiting up to 60s. (2) When the catalog backfill genuinely yields nothing, surface a "find image / reimagine" affordance on the tile so the user isn't stuck. (3) Local-dev only: replace or remove the stale singular `SERPER_API_KEY` in `ScentCast.env` so local testing matches prod's pool. Do NOT treat Serper credits as the production cause.
**Confidence:** High (mechanisms a–d confirmed in code).

## Cross-cutting notes
- **Bugs 3 + 4 are one UX problem** — selection feedback and the select→add gap; fix together in `FragranceCapture.tsx` (item render + sticky CTA + distinct `is-selected` in `index.css`).
- **Bugs 1 + 2 share the missing-intelligence theme**: no query normalization (Bug 1) and no result ranking (Bug 2), both in the SPA between `searchFragrances` and `setMatches`. A small client-side query-normalize + rank module addresses both.
- **Bug 5 is a UX/timing gap, not infra.** The deferred-resolution design returns an empty `imageUrl` on the immediate save and relies on the background catalog backfill + the 60s wardrobe poll (`batchHydrateImageUrls`) to fill the tile — so a fresh save shows "No image" for up to ~60s *by design*, even with a healthy Serper key. The production Serper pool key is fine; the stale `ScentCast.env` singular key is local-dev only. Fix the no-loading-state + slow-self-heal, not the credits.
- Suggested order: Bug 1 normalization → Bug 2 ranking/latency → Bugs 3/4 UX together → Bug 5 loading-state/immediate-rehydrate.
